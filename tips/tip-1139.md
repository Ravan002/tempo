# TIP-1139: Access List Lane and State Access Pricing

## Abstract

This TIP introduces a new Tempo transaction version with read/write declarations
for account metadata, persistent storage, and bytecode. A signed marker selects a
100 million execution-gas access list lane, while the general lane is reduced to
16.7 million execution gas. Declared resources pay their access price once, at
declaration, and every later access costs the 100-gas warm price. Payment lane
transactions carry no list; they are priced as if they had a complete one.
Undeclared accesses remain executable at higher serial prices; they do not
invalidate the transaction or change its lane.

## Motivation

General-lane capacity limits contract throughput, while serial state dependencies
make execution expensive and difficult to predict. Transaction-level declarations
let clients prefetch independent resources before execution, protecting proposers
as well as validators. They also work with multi-concurrent proposers (MCP), where
a block-level access list alone cannot provide the same advance information.

Read/write and account/bytecode distinctions give applications an incentive to
identify their actual resource needs. Complete lists also provide a basis for
future deterministic parallel execution, but this TIP introduces neither a
parallel scheduler nor a consensus-visible cache or database migration.

### Transitional pricing

This TIP is transitional. Tempo state is currently small enough that most of it
is served from memory, so undeclared accesses are not yet as expensive as they
will become as state grows. The prices here are therefore not derived from
worst-case database latency, and the serial prices are deliberately below what a
full cost model for a large state would require. Their purpose is to establish
the incentive structure early: declared and payment lane accesses are cheap,
undeclared accesses are noticeably more expensive, and the general lane is small.
Applications that migrate to complete declarations now will be unaffected when
later TIPs move undeclared and general-lane prices toward their full cost.

## Assumptions

- [TIP-1016](./tip-1016.md) execution/state gas separation and
  [TIP-1060](./tip-1060.md) storage credits are active before this TIP.
- All clients classify transactions and charge gas from signed declarations and
  consensus state, independent of local cache residency or successful prefetch.
- At activation this TIP amends, for type `0x77` and for all transactions as
  applicable: [TIP-1010](./tip-1010.md)'s general gas limit and transaction gas
  cap (both 30,000,000 to 16,700,000); TIP-1016's `max_transaction_gas_limit`
  (set to 16,700,000); the [TIP-1045](./tip-1045.md) payment classifier
  (extended to type `0x77`, still requiring an empty access list); and
  TIP-1060's SSTORE execution residual and retained net-metering refunds
  (replaced by section 3). All other rules of those TIPs remain in force.
- The activation fork is selected through the TIP process. `protocolVersion: TBD`
  denotes an unscheduled proposal, not an unresolved execution rule.

# Specification

## 1. Transaction format

Introduce EIP-2718 type `0x77` for the extended Tempo transaction and signing
prefix `0x79` for its fee payer. Type `0x76` and its `0x78` fee-payer domain retain
their existing encodings and signing semantics.

The signed wire format is:

```text
0x77 || rlp([
    chain_id, max_priority_fee_per_gas, max_fee_per_gas, gas_limit,
    calls, nonce_key, nonce, valid_before, valid_after, fee_token,
    fee_payer_signature, tempo_authorization_list, key_authorization,
    flags, extended_access_list, sender_signature
])
```

All 16 fields are required. Shared fields use the encodings and validation rules
of [TIP-0001](./tip-0001.md) and its active amendments. `tempo_authorization_list` is
the field named `aa_authorization_list` in TIP-0001's prose; the name here
follows the implementation. Absent `key_authorization`
is an empty RLP byte string instead of an omitted field. Absent validity bounds,
fee token, or fee-payer signature use their existing empty-string encodings.
`calls` is non-empty. There is no separate EIP-2930 `access_list` in this version.

`flags` is a canonical RLP unsigned integer. Bit 0 is `access_list_lane`; all other
bits MUST be zero. Thus only integer values 0 and 1 are valid, with zero encoded
as the empty RLP string. Invalid lengths, extra fields, non-canonical RLP, unknown
flags, or malformed declarations make the transaction invalid before execution.

### Extended access list

```text
extended_access_list = [account_entry, ...]
account_entry = [address, account_mode, code_read, storage_entries]
storage_entries = [[key, mode], ...]
```

- `address` is exactly 20 bytes; `key` is exactly 32 bytes.
- `account_mode` is integer 0 (none), 1 (read), or 2 (read/write).
- `code_read` is integer 0 (none) or 1 (read).
- Storage `mode` is integer 1 (read) or 2 (read/write).
- Account entries are strictly ordered by unsigned address bytes. Storage entries
  are strictly ordered by unsigned key bytes within each account. Duplicates are
  invalid; an entry with no account, code, or storage declaration is invalid.
- At most 512 account entries and 4,096 storage entries are permitted. The RLP
  encoding of the complete extended list MUST be at most 65,536 bytes; the signed
  EIP-2718 transaction MUST be at most 131,072 bytes. All limits apply together.

An account declaration covers nonce, balance, existence, and code hash, but not
code bytes or arbitrary storage. A storage declaration identifies the actual EVM
storage context; a code declaration identifies the address supplying code. For
`DELEGATECALL`, those addresses may differ. Delegation targets require their own
code declarations. Empty and nonexistent accounts can also be declared.

Write permission includes reads. Read permission does not cover writes. All
batched calls and nested frames use the same immutable list. Transient storage,
stack, memory, calldata, and block-environment reads need no declaration.

### Hashes and signatures

Let `U` be the first 15 fields of the signed list, excluding `sender_signature`.
For the sender signing hash, replace `fee_payer_signature` in `U` with the empty
RLP byte string when unsponsored. When sponsored, replace it with the single byte
`0x00` and replace `fee_token` with the empty RLP byte string, preserving the
existing sponsor's ability to select the token. This `0x00` is a signing
placeholder, not a valid onchain fee-payer signature.

```text
sender_hash = keccak256(0x77 || rlp(sender_U))
fee_payer_hash = keccak256(0x79 || rlp(fee_payer_U))
transaction_hash = keccak256(signed_wire_bytes)
```

`fee_payer_U` includes the actual fee token and replaces `fee_payer_signature`
with the recovered 20-byte sender address. Both signing hashes include `flags`,
the full extended list, authorization fields, and all other fields in order.
As for type `0x76`, a sponsor therefore commits to every field except the
sender signature.
Signature formats, key authorization, and recovery follow the existing active
Tempo rules. The sponsor signature remains secp256k1. Expiring-nonce identity is
`keccak256(0x77 || rlp(sender_U) || sender_address)`.

Receipts use EIP-2718 type `0x77` with the same receipt payload as Tempo type
`0x76`. The transaction hash, sender signing hash, and sponsor signing hash MUST
NOT reuse any type `0x76` domain.

## 2. Lane classification and limits

Classify once, before execution, in the following order:

1. A type `0x77` transaction with `flags & 1 == 1` is an access list transaction.
2. Otherwise, apply the active [TIP-1045](./tip-1045.md) payment classifier. For
   type `0x77`, apply its Tempo batched-call rules, with the extended list taking
   the place of `access_list`: a type `0x77` transaction is payment-eligible only
   if its extended list is empty. Authorization restrictions, call allow-list, and
   key-authorization size bound still apply.
3. Every remaining transaction is general.

Payment lane transactions continue to require an empty access list, as in
TIP-1045: a non-empty legacy EIP-2930 list or a non-empty extended list makes an
otherwise payment-shaped transaction general. Payment lane transactions do not
need declarations because their accesses are inferred (section 3). Legacy
EIP-2930 lists cannot select the access list lane.

| Parameter | Execution gas |
| --- | ---: |
| Total block limit | 500,000,000 |
| General lane limit | 16,700,000 |
| Access list lane limit | 100,000,000 |
| Per-user-transaction execution cap, all lanes | 16,700,000 |

The general limit is the literal 16.7 million parameter, rather than the
16,777,216 cap specified for Ethereum in
[EIP-7825](https://eips.ethereum.org/EIPS/eip-7825). The per-transaction cap is
used as `max_transaction_gas_limit` in TIP-1016's reservoir initialization and
intrinsic/calldata-floor checks. A transaction's signed `gas_limit` may exceed it
to pay for state gas; excess gas does not extend its execution budget.

Let `g(tx)` be the transaction's execution-gas block contribution under TIP-1016,
including intrinsic execution gas and the calldata floor. For a valid block:

```text
sum(g(tx) for all transactions) <= 500_000_000
sum(g(tx) for general transactions) <= 16_700_000
sum(g(tx) for access list transactions) <= 100_000_000
```

Each user transaction consumes exactly one lane plus the total budget. The
payment lane consumes remaining total capacity, not an additional independent
500 million allocation. Unused access list or general capacity does not raise
the other's cap. The new lane does not add gas to the total block budget.

This TIP preserves system transaction accounting.
[TIP-1046](./tip-1046.md) disables validator subblocks from T4; this TIP does not
re-enable them or introduce a subblock allocation. At activation, the shared
budget is zero and proposer transactions use the total 500 million budget with
the additional lane caps above. Historical shared-budget rules remain unchanged
for historical replay. All sums use the final consensus execution order.

The marker is the sender's claim that its declarations cover execution, not a
consensus requirement that coverage be perfect. A marked transaction with an
empty or incomplete list is still valid and stays in the access list lane. It
pays serial prices for missing resources as specified below. Builders MAY decline
such transactions as local policy, but validators MUST NOT reject them merely
for incomplete coverage. There is no deterministic-parallelism guarantee in this
TIP.

## 3. State access pricing

Every access to a resource that is already warm for the required kind costs
**100 execution gas**, in every lane. A resource becomes warm either by
declaration (its price is then paid in intrinsic gas, section 4) or by paying a
first-access charge during execution. The schedule is:

| Operation | Declared (charged once at declaration) | Payment lane, inferred (first access) | General lane, undeclared (first access) | Access list lane, undeclared (first access) |
| --- | ---: | ---: | ---: | ---: |
| SLOAD / account metadata read | 2,000 | 2,000 + 100 | 4,000 | 20,000 |
| SSTORE / account metadata write | 5,000 | 5,000 + 100 | 10,000 | 50,000 |
| Bytecode load (account read + code component) | 5,000 | 5,000 + 100 | 10,000 | 50,000 |

A bytecode load is charged in two steps (see "Accounts, code, creation, and
precompiles"): an account read, then, only if the account has non-empty code, a
code component equal to the bytecode row minus the read row (3,000 declared or
inferred, 6,000 general lane undeclared, 30,000 access list lane undeclared).
The table shows the total for a target that is cold for both.

The declared column is charged once per declared resource and permission in the
transaction's intrinsic gas; every access within the declared permission then
costs 100, including the first. The payment lane column charges the same declared
price, but at the first access instead of upfront, plus the 100-gas access. The
undeclared columns are complete execution charges for the first logical access of
the indicated kind; later accesses of that kind cost 100. Warmth is
transaction-local consensus bookkeeping, not physical cache residency.

Track read and write warmth separately for account metadata and each persistent
storage slot, and code-read warmth separately for each code-source address. An
undeclared first read uses the read row and marks read warmth. An undeclared
first write uses the write row and marks both read and write warmth; a prior read
does not make the first write warm. This ensures a read-only declaration cannot
avoid the undeclared first-write price. The first undeclared code load of an
address with non-empty code pays the code component and marks code warmth.

### Initial warmth

Initial account/storage read warmth follows the active EVM transaction rules,
including the top-level target and legacy EIP-2930 prewarming. In addition, each
type `0x77` declaration makes its resource warm from the start of execution:

- `account_mode` 1 makes the account read-warm; 2 makes it read- and write-warm.
- `code_read` 1 makes the address code-warm and account read-warm.
- Storage `mode` 1 makes the slot read-warm; 2 makes it read- and write-warm.

Declaration warmth applies in every lane and is transaction-level: it is never
removed by frame rollback. Payment lane inferred warmth (below) behaves the same
way. Speculative prefetch or cache residency never makes a resource warm.
Other warmth acquired during execution is marked only after its access charge
is paid, before the lookup, and is journaled with call frames under the
existing EVM access-set rollback rules. Successful frames propagate it, while
reverted or exceptionally halted frames discard their additions. Batched calls
share the transaction's surviving warmth. Envelope processing retains its
existing read warming behavior and charges; it does not prepay a first
user-execution write.

Previously touching a resource never upgrades its signed permission.

### Payment lane inferred access list

Payment lane transactions carry no access list (section 2). Their calls are
restricted by the TIP-1045 allow-list to bounded native TIP-20 operations, whose
resources follow from the call arguments, native storage layouts, and a bounded
number of native metadata lookups. A payment lane transaction is therefore
priced as if it carried a complete access list: no access in the payment lane
pays an undeclared price.

The declared price is charged lazily, at the first access that requires a given
permission, because there is no list to charge upfront:

- The first read of an account or slot costs 2,000 + 100 and marks it read-warm.
- The first write of an account or slot costs 5,000 + 100 and marks it read- and
  write-warm. If a read of that resource was already charged, the write instead
  costs 3,000 + 100, so the total equals one read/write declaration.
- A code load or native dispatch first pays the account read as above (or 100
  if the address is already read-warm, for example the top-level target under
  the active EVM rules). If the address has non-empty code that is not yet
  code-warm, it additionally pays the 3,000 code component.
- Every later access of a warm kind costs 100.

This yields the same total as an explicit complete list, without per-byte list
charges. Like declaration warmth, inferred warmth is transaction-level: once a
resource's inferred price has been charged, it stays warm for that permission
even if the frame that charged it reverts, and the charge is not refunded.

The inference applies to all persistent accesses made while executing a payment
lane transaction, including native registry/policy, receive-policy/guard,
storage-credit, and keychain dependencies of the native TIP-20 implementation.
Consensus pricing depends only on the transaction's lane, not on whether a client
could or did derive the resources in advance. It does not bypass payment
classification, state-creation charges, execution limits, or payment-discount
conditions, and it does not apply to TIP-20 calls made outside the payment lane:
general and access list lane transactions use their own columns, and should
declare TIP-20 resources explicitly to receive declared prices.

### Missing declarations and insufficient write permission

Select and deduct the appropriate execution charge before the resource lookup or
mutation. In the access list lane, a first undeclared read costs 20,000; a first
write without write permission, including to a slot declared read-only, costs
50,000. A missing code declaration costs a 30,000 code component on the first
load of non-empty code, on top of the 20,000 account read unless the address is
already read-warm. In the general lane the corresponding charges are 4,000,
10,000, and a 6,000 code component. Later
accesses of the same warm kind cost 100, without changing their declaration
coverage. Execution continues normally, including ordinary EVM return/revert
behavior.

A missing declaration is neither a revert nor invalid inclusion. If the selected
charge cannot be paid, the current frame exceptionally halts with ordinary
out-of-gas semantics, before the lookup or mutation. A parent may handle a child
failure under normal EVM call rules. TIP-1016 governs gas-reservoir restoration,
state rollback, and unused-gas return. No operation silently receives the cheaper
price, promotes a resource to declared, or switches lanes after a miss.

For example, a marked transaction declaring a slot read-only pays 2,000 at
declaration, 100 for every SLOAD including the first, 50,000 for its first
SSTORE, and 100 for subsequent writes. The first-write price applies even if that
write sets the same value; reversion journals warmth acquired during execution as
described above.

### Storage and refunds

SLOAD pays the first-read price or 100 when read-warm. SSTORE pays the first-write
price or 100 when write-warm, including no-op, clean, dirty, clear, recreate, and
restore-to-original transitions. The SSTORE charge includes loading the
original/current slot values and the write;
it MUST NOT add a separate SLOAD charge for the internal read. Explicit SLOAD
instructions remain separately charged. The EVM static-context prohibition and
2,300-gas SSTORE sentry check remain in force before attempting a write.

#### Restore-to-original refunds

Each write price in section 3 is split into an **access component**, equal to
the read price of the same column, and a **write component**, equal to the
remainder:

| Column | Access component (never refunded) | Write component (refundable) |
| --- | ---: | ---: |
| Declared / payment lane inferred | 2,000 | 3,000 |
| General lane, undeclared | 4,000 | 6,000 |
| Access list lane, undeclared | 20,000 | 30,000 |

The access component pays for locating and loading the slot, which happens
whether or not the write is later undone. The write component pays for the state
change, which is avoided if the slot ends the transaction unchanged. The column
is the one that priced the slot's write permission: declared for a slot declared
with mode 2, payment lane inferred for payment lane transactions, and otherwise
the transaction lane's undeclared column (including a slot declared read-only).

At the end of transaction execution, for every persistent storage slot that was
the target of at least one SSTORE whose frame and ancestors did not revert or
exceptionally halt, and whose
final value equals its original (transaction-start) value, add that slot's write
component once to the transaction's execution refund counter. This includes
no-op writes and `X -> Y -> X` and `0 -> Y -> 0` sequences, and is evaluated only
on the final value, so `X -> Y -> X -> Y` receives no refund. The access
component, warm 100-gas charges, account metadata writes, and SSTOREs in reverted
or exceptionally halted frames are never refunded.

These refunds replace the EIP-2200 net-metering refunds retained by TIP-1060,
including its restore-to-original refunds; no other SSTORE execution refund
applies. The nonzero-to-zero clearing refund remains zero as in TIP-1060.
Because a refund never exceeds the write component already charged for that slot,
refunds cannot erase access charges, including serial-access charges, and a
transaction's refunded block execution gas still covers every lookup it
performed. Unused gas and ordinary REVERT still follow the existing return rules.

TIP-1060's present-to-new storage-credit transitions and TIP-1016's state gas are
unchanged: a nonzero-to-zero transition mints a credit; a zero-to-nonzero
transition consumes a credit or pays 245,000 state gas according to storage mode.
The section 3 SSTORE price replaces the prior execution residual; no additional
5,000 execution residual is charged. State-gas rollback and credit settlement are
still journaled. Credit bookkeeping performed solely by the protocol as part of
that transition is included in the SSTORE execution price, avoiding recursive
charges for the implementation of the credit mechanism. Direct user calls to the
storage-credits precompile have no exemption.

### Accounts, code, creation, and precompiles

`BALANCE`, `EXTCODEHASH`, and any other logical account metadata read use the read
row. Account metadata writes, including value transfers and nonce changes
performed by user execution, use the first-write row or 100 when write-warm,
including attempted no-op writes. Internal
loads solely required to implement a metadata write are included in that write
price. Storage-owner bookkeeping solely needed for SLOAD/SSTORE is included in
the corresponding storage operation, rather than charged as an extra account
read.

Each `CALL`, `CALLCODE`, `DELEGATECALL`, `STATICCALL`, `EXTCODESIZE`, and
`EXTCODECOPY` is charged in two steps, each deducted before its lookup:

1. **Account read.** Pay the account read price, or 100 when account-read-warm,
   then look up the target account and its code hash.
2. **Code component.** If the code hash is non-empty, pay the code component
   (bytecode row minus read row for the applicable column), or 100 when
   code-warm, then load the code. If the code hash is empty, there is no second
   step: no code is loaded and no code component is charged.

An address without code therefore costs only an account read, and needs only an
account declaration. A cold call to a contract costs the full bytecode row, as in
the section 3 table. Account read warmth and code warmth are tracked separately,
so a target that is already read-warm (for example via `BALANCE` or the EVM's
initial warm set) pays 100 plus the code component. `EXTCODEHASH` remains a
plain account read. These charges replace the opcodes' previous base and
cold/warm target-access charges. Memory expansion,
copying, value-transfer/account-write charges, account-creation state gas,
call stipend, and the 63/64 forwarding rule remain applicable separately. Deduct
these caller costs before computing forwarded gas.

Each EIP-7702 delegation hop is charged by the same two steps for the address
whose code it loads. The top-level entry into each Tempo
batch call is charged by the same rules, even though it has no enclosing CALL
opcode. Insufficient top-level gas fails the call under Tempo batch atomicity.
For native precompile dispatch, no code bytes are loaded: charge only step 1,
the account read or 100 when account-read-warm, then charge the precompile's own
work and persistent accesses.

`CREATE` and `CREATE2` retain their existing computation, hashing, initcode, and
code-deposit prices and state-gas split. Additional account reads/writes use this
TIP's rows. Newly created code is code-warm from the start only if its
deterministic address was declared with `code_read`; otherwise its first load
pays the lane's undeclared code component and later code-warm loads cost 100.
`SELFDESTRUCT` retains its active deletion restrictions and intrinsic opcode
charge, with account reads/writes charged under this TIP. Transient storage
pricing is unchanged. Operations not modified here retain their active prices.

Native precompile persistent reads/writes use the same resource identities as
EVM storage/account operations. In the payment lane they use inferred pricing;
otherwise they use the ordinary declaration/lane rules. Charges follow the
native storage interface: each native storage write operation, including atomic
read-modify-write operations such as balance increment and decrement, is one
write whose internal read of the current value is bundled in its price. A
native storage read operation is a read, even when the same slot is written
later; a read followed by a write pays both (in the payment lane, the write then
pays only the 3,000 difference). Native implementations MUST NOT split one
logical storage operation into separately charged reads and writes, and the
operation sequence of each native method is part of its gas specification.
Native precompile computation charges remain payable, excluding any old
storage-access components now replaced by this TIP.

### Protocol-managed accesses

Envelope processing retains its existing bounded charges and does not require
user declarations: signature/key authorization validation, authorization-list
processing, envelope nonce validation/increment, fee-token selection, fee
reservation, fee refund/distribution, and protocol storage-credit settlement.
Their existing intrinsic and fee charges retain TIP-1016's execution/state split.
This avoids requiring the sender to know a sponsor-selected fee token or a future
proposer's fee recipient, and avoids circular gas charging during fee refunds.

This exception applies only while performing these protocol actions outside user
calls. The same contracts/resources accessed from a user call or nested precompile
are metered normally. No arbitrary target, entire contract storage, or
user-directed callback is implicitly declared. Envelope algorithms, authorization
bounds, and fee routing remain the active protocol algorithms; this TIP does not
expand their permitted work. A protocol action invoking user code MUST charge that
code and its persistent accesses under the user-execution schedule.

## 4. Declaration costs and prefetching

In addition to existing intrinsic transaction charges, type `0x77` pays:

```text
16 * len(rlp(extended_access_list))
+ 100
+ 2_000 * count(entries with account_mode == 1, or account_mode == 0 and code_read == 1)
+ 5_000 * count(entries with account_mode == 2)
+ 3_000 * count(entries with code_read == 1)
+ 2_000 * count(storage entries with mode == 1)
+ 5_000 * count(storage entries with mode == 2)
```

All terms are execution gas. The 100-gas term covers flags and list validation;
every encoded list byte costs 16 gas, including zero bytes and RLP overhead.
The per-entry terms are the declared prices from section 3: they are the
complete first-access charges for the declared resources and permissions, and
every access within a declared permission then costs 100. A `code_read`
declaration includes the account read it depends on, so an entry declaring code
costs 5,000 with or without an account read (8,000 with account write). Unused
declarations pay
in full and receive no refund. These charges do not replace the calldata floor.

For example, an empty list encodes as `0xc0` and adds 116 intrinsic execution
gas. A list containing one account-read entry with no code or storage entries
encodes in 26 bytes and adds `16 * 26 + 100 + 2_000 = 2_516` gas. These charges
remain payable even when execution never touches the declared account.

Clients MUST validate bounds, canonical ordering, signatures, fee authorization,
and intrinsic gas before launching prefetch work. Prefetch only exact listed
resources or, for payment lane transactions, native TIP-20 resources derived from
the allow-listed calls through bounded native metadata lookups; do not fetch all
storage for an address or follow unrelated unlisted code/delegation targets.
Queue depth and memory are bounded local settings.
Clients MAY skip or cancel prefetch without changing execution or gas prices.
Read/write declarations do not license optimistic parallel execution: a serial
miss can introduce an unexpected conflict, so any speculative executor must
validate actual conflicts and replay to the canonical serial result.

## 5. Fees, activation, and compatibility

All three lanes use the active gas-price and sponsorship rules; this TIP creates
no separate base fee. The [TIP-1067](./tip-1067.md) controller uses total block
execution gas from all lanes through TIP-1016's header `gasUsed`. Its target,
floor, cap, and adjustment formula remain unchanged. A single base fee across
lanes is intentional: the small general lane is expected to clear mostly through
priority fees, which encourages migration to the access list lane.

Unmarked type `0x77` payments are eligible for [TIP-1059](./tip-1059.md) discounts
only when they satisfy its active call-shape and signed gas-limit conditions.
A marked access list transaction
receives no payment discount, even if its calls are payment-shaped. Settlement
and builder fee comparison use the same charged amount.

At the activation fork, accept type `0x77`, apply these lane limits and prices,
and revalidate the pool. Before activation, type `0x77` is unsupported and earlier
transaction/lane/gas rules remain unchanged. Historical replay selects the rules
for the historical block. No new block-header field is needed; lane gas is
computed from transaction classification and execution.

Legacy transactions remain supported after activation but pay the applicable new
operation prices. Wallets and sponsors MUST re-estimate gas. Incomplete lists can
cost more gas after another transaction changes a branch or delegation target;
clients should regenerate a list or increase authorized gas when resubmitting.
Contracts forwarding fixed gas amounts require compatibility testing. State gas
remains outside the execution cap, preserving maximum-size deployments under
TIP-1016 subject to their actual execution budget.

and initially cold user-path slots. The top-level native target is account-read-warm.

calldata, signature, event/computation, and envelope costs; these must be added
for complete receipt gas and fees. State gas is shown separately.

| Unlimited allowance read in `transferFrom`, incremental to the transfer | 2,100 | 2,100 | 0 | 0 |

These TIP-20 results are for payment lane transactions, priced by the inferred
access list: three policy/pause reads at 2,100, a sender balance write at 5,100,
and either an existing recipient balance write at 5,100 or, on the new-balance
path where the snapshot shows a separate read before the write, 2,100 + 3,100.
There is no per-byte list charge. Baseline can be lower when envelope processing
has already warmed a balance; proposed first user writes still pay the write
price, while read-warm accesses cost 100. TIP-20 calls outside the payment lane
use their lane's declared or undeclared prices instead. Unmarked payment
transactions retain eligibility for the active payment discount; selecting the
access list lane does not confer it.

For ordinary contract execution, the following results include the per-entry
declaration charge but exclude per-byte list charges (about 560 gas per storage
entry, plus its account entry) and unchanged instruction overhead:

| Storage sequence | Baseline execution gas | General lane, undeclared | Declared, any lane | Access list lane, undeclared |
| --- | ---: | ---: | ---: | ---: |
| Cold SLOAD | 2,100 | 4,000 | 2,100 | 20,000 |
| Warm SLOAD | 100 | 100 | 100 | 100 |
| Ten reads of one initially cold slot | 3,000 | 4,900 | 3,000 | 20,900 |
| Cold existing-slot write followed by restore to its original nonzero value (e.g. a reentrancy guard), net of refund | 2,300 | 4,100 | 2,200 | 20,100 |

Warm accesses retain their 100-gas price. Write/restore patterns refund only the
write component, so their net cost is the access component plus warm charges. Batching amortizes
transaction/list overhead and reuses surviving warm resources. New token balances
and allowances retain their storage-credit/state-gas
charges. The general lane has 44.3% less capacity before repricing, while the
100 million access list lane shares the existing 500 million total budget.
Custom policies, virtual recipients, access keys, guarded delivery, and warm
batches require their own full-transaction estimates. Validate those paths using
the [TIP-20 gas scenarios](../crates/node/tests/it/gas/tip20_transfers.rs) before
activation; a fixed gas price translates gas changes into fee changes, while
actual fees also depend on the active fee and discount rules.

# Alternatives Considered

- Raising the general lane alone increases capacity without incentivizing advance
  knowledge of expensive serial dependencies.
- Block-level lists do not supply each proposer with a signed transaction-level
  declaration before it begins execution.
- Ordinary EIP-2930 lists lack account/code and read/write distinctions.
- Rejecting or reverting on missing declarations makes inclusion sensitive to
  simulation state. Serial prices instead bound unexpected work and keep
  transaction validity independent of perfect simulation coverage.

A consensus-visible cache, deterministic parallel scheduler, and state database
redesign require separate TIPs. This specification activates none of them.

# Tooling

SDKs and signing libraries MUST support type `0x77`, the canonical list, flags,
and both signature domains. Existing raw-transaction submission and receipt RPCs
handle the new EIP-2718 type. JSON transaction objects expose `type: "0x77"`,
`flags` as a hex quantity, and `extendedAccessList` as an array of objects with
`address`, `accountMode`, `codeRead`, and `storageEntries`; storage entries contain
`key` and `mode`. Modes and `codeRead` are hex quantities corresponding to the wire
integers. For this type the old `accessList` field is absent or empty; supplying a
non-empty value is invalid. Responses emit all extended fields explicitly.

Add `tempo_createExtendedAccessList(transaction, blockSelector)`. It accepts the
usual call/simulation transaction object and block selector, simulates against
that state without committing changes, and returns `extendedAccessList`, `gasUsed`,
`executionGasUsed`, `stateBlockHash`, and `serialAccesses` (an empty array when
there are no misses). The block selector resolves a mined block by number, hash,
or `latest`, `safe`, or `finalized`; `pending` is rejected with `-32602` so the
reported state has a block hash. Omitted type, flags, and list default to `0x77`,
`0x1`, and an empty extended list. Other types are rejected. Other simulation
field defaults follow `eth_call`. `gasUsed` is TIP-1016's post-refund total gas;
`executionGasUsed` is its block execution-gas contribution. Gas values are hex
quantities. Reads and
writes actually attempted, including reverted paths, are collected; writes
upgrade the collected resource mode to 2. Code loads of addresses without code
are collected as account reads, not `code_read`. Account reads and storage reads
that are already warm under the EVM's initial warm set (for example the sender,
top-level call targets, and precompiles) are omitted, because declaring them
costs gas without changing their price; write and code declarations for those
resources are still collected. Results are canonical and obey the
wire bounds. Re-simulate the collected list under the selected flags to report
its gas cost. If gas-dependent control flow introduces further misses in that
second simulation, return them in `serialAccesses`, rather than claiming complete
coverage. Each entry in that array has `address`, `kind` (account/storage/code),
`mode`, and `key` for storage. Ordinary simulation errors use the existing RPC
error representation; list/transaction overflow uses invalid-parameters error
`-32602`. Standard `eth_estimateGas` uses submitted declarations, payment lane
inference for payment-eligible transactions, and the applicable undeclared
prices, without changing the signed list.

A generated list is advisory and bound to its reported simulation state, not an
inclusion guarantee. Existing `eth_createAccessList` remains an EIP-2930 API.

# Observability

No new contract event is required. Clients MUST emit a structured execution
summary with block hash, transaction hash, lane, execution gas, declaration gas,
and serial-access count by account/storage/code and read/write operation. Block
summaries MUST report total and per-lane execution gas so caps can be checked.

Execution traces MUST identify access coverage as explicit, payment-lane
inferred, or uncovered. Clients MUST provide serial-access details in execution traces: resource kind,
address, storage key where applicable, required mode, declared mode, charged gas,
and frame depth. Out-of-gas traces distinguish inability to pay a serial price
from an application REVERT. Resource identities MUST NOT be unbounded metric
labels. Clients SHOULD measure prefetch queue depth, bytes, latency, and failures;
these local observations never determine consensus pricing.

# Threat Model

Senders and sponsors can omit resources, understate write permissions, or pad
unused declarations. Serial prices, upfront declaration charges, strict bounds,
and signature binding limit those behaviors. Payment lane inference cannot be
used for arbitrary execution, because the payment classifier admits only
allow-listed native TIP-20 calls with an empty list. An incomplete list never lets the
sender escape the gas cap by changing lanes. Proposers can misclassify or exceed
budgets; validators independently recompute classification and execution totals.

RPC simulation and local prefetch are advisory. Cache hits, previous reads, and
speculative scheduling do not upgrade permissions. Implementations check and
charge before accessing state. This TIP does not claim that declarations alone
prove denial-of-service resistance or conflict-free parallel execution.

With the parameters above, the cheapest undeclared lookup is a read: 4,000 in
the general lane and 20,000 in the access list lane. Payment lane accesses are
inferred and never undeclared. The worst case is therefore about
`16_700_000 / 4_000 + 100_000_000 / 20_000`, roughly 9,150 undeclared lookups per
block after transaction overhead, compared with roughly 14,300 cold SLOADs in
the current 30 million general lane. Declared and inferred lookups are
prefetchable but not free: about 50,000 declared reads fit in the access list
lane, and the payment lane may need tens of thousands of inferred lookups in two
or three dependent stages. Future TIPs that reprice undeclared access should
state a target for worst-case undeclared lookups per block at an assumed
lookup latency and derive prices from it. The prices
are transitional (see Motivation): they set incentives for a growing state rather
than covering worst-case database latency, and later TIPs are expected to raise
undeclared and general-lane prices.

# Invariants and Validation

1. Sender and sponsor hashes bind flags and every declaration. Changing either,
   or confusing the `0x76`/`0x77` domains, invalidates signatures.
2. Non-canonical/oversized lists are invalid; incomplete lists are valid. Legacy
   lists never qualify for the access list lane. Payment lane transactions have
   empty lists.
3. Declared resources pay their declared price exactly once, in intrinsic gas,
   and every access within the declared permission costs 100. Payment lane
   transactions pay the same total per resource, charged at first access. First
   writes without write permission and first undeclared accesses in the access
   list lane pay serial prices before access; insufficient gas causes ordinary
   frame out-of-gas, with no lane change.
4. Warm accesses cost 100 in all lanes. Reads cannot warm a first write, and
   local cache hits or prefetch cannot warm any access. Declaration and payment
   lane inferred warmth survive frame rollback; other warmth is journaled.
5. All SSTORE transitions pay the first-write price or 100 when write-warm.
   Restore-to-original refunds return only the write component, so refunds never
   cancel access or serial-access charges; permanent state still follows
   storage-credit/state-gas rules.
6. Exactly one lane and the total budget include each user transaction, using
   TIP-1016 execution gas. State gas cannot enlarge execution capacity.
7. Protocol-envelope exceptions cannot be reached by arbitrary user calls.
8. Payment discounts apply only to eligible payment-lane transactions, and
   builder comparison agrees with settlement.

Reference tests MUST cover all permission/resource combinations, empty lists,
read-then-write misses, warm repeated operations, no-op/clear/restore SSTOREs,
restore refunds in every column (including `X -> Y -> X -> Y`, restores inside
reverted frames, and read-only-declared slots),
credit modes, account creation, delegation, two-step code loads (including
`EXTCODESIZE` and calls on addresses without code and on read-warm targets),
precompiles, sponsored
fee-token selection, nested reverts/OOG, stale simulations, exact list/byte/gas
boundaries, signature domain separation, and activation/historical replay. Tests
MUST cover payment lane inference for all native TIP-20 dependency paths
(including read-then-write upgrades and reverted frames), rejection of non-empty
lists from the payment lane, TIP-20 calls outside the payment lane, and
redundant/read-only explicit entries.

Release readiness requires independent agreement on transaction/signing and gas
fixtures, adversarial state/code/prefetch benchmarks within the block timing
budget, and testnet validation of estimates, payments, and maximum-size contract
deployment. These are validation gates for the specified rules, not alternative
execution semantics.
