# TIP-1008: Zone Deposit Overflow Escrow

## Abstract

An otherwise-valid zone deposit that exceeds public queue capacity succeeds into the existing `ReceivePolicyGuard` instead of reverting. The zone can later claim and enqueue it atomically, or its originator can cancel through the portal. Deposits with available capacity follow their existing path.

## Motivation

The deposit cap bounds mandatory zone execution and proof work, but a temporary backlog should not fail a user's Tempo payment. This is especially useful for [TIP-1094 zone virtual addresses](https://github.com/tempoxyz/tempo/pull/7746): a wallet or exchange sends an ordinary TIP-20 transfer without constructing a portal call, and should not need to retry solely because the zone queue is full.

[TIP-1028](./tip-1028.md) already provides custody, receipt authentication, and single-use claims. This TIP adds capacity exhaustion as a new receipt source and keeps waiting deposits outside the mandatory queue.

## Assumptions

- Activation updates the guard, native token helpers, and canonical portal runtime together. Existing receipts and queued deposits retain their meaning.
- Native code authenticates portals against the factory registry and canonical runtime. That runtime exposes no arbitrary call/delegatecall facility. Virtual deposits additionally depend on TIP-1094, including its separate routing implementation.
- Admission requires operating zone infrastructure and settlement that reopens capacity. Cancellation requires Tempo execution and the existing guard's claim-time token/policy checks; it does not require sequencer cooperation.

# Specification

## Overflow handling

Apply this change to public ECIES deposits and TIP-1094 virtual-address transfers and mints. Keep withdrawal bounce-backs, forced exits, and withdrawal-callback deposits on their existing paths, including their reserved capacity and requirement to append a deposit.

Run the ordinary deposit validation, funding, and fee payment. All non-capacity failures still revert. In particular, reject a receive-policy failure before funding rather than treating independently blocked funds as a funded portal deposit. If public capacity is available, enqueue normally. Otherwise move the net deposit amount into the guard and create an overflow receipt. Protect the funding/escrow branch against reentrancy. Creation, funding, fees, and events are atomic; failure rolls everything back.

The public cap remains based on `depositCount - lastProcessedDepositNumber`, preserving the withdrawal reserve. Pending receipts do not change that count or the queue hash. A new Tempo block does not restore capacity; accepted settlement does. The normal deposit fee is paid once at submission, including for overflow; neither admission nor pre-admission cancellation charges it again or reverses it.

## Receipts

Append `ZONE_CAPACITY = 3` to `BlockedReason`, preserving the existing values. Receive-policy evaluation never returns this reason.

Reuse `ClaimReceiptV1`, the nonce, receipt hash, balance mapping, and `claim` unchanged in layout and authority semantics. Set `recipient` and `recoveryAuthority` to the literal portal, `originator` to the original debited owner or mint caller, and `kind` to the authenticated transfer/mint provenance. Store the net amount in the existing guard balance mapping. Do not use the virtual destination as the receipt recipient, since guard recipient resolution is for TIP-1022 addresses.

Set the receipt's `memo` to:

```text
keccak256(abi.encode(depositType, deposit))
```

Here `depositType` and `deposit` are exactly the type tag and struct that would have been appended to the existing queue: ECIES `Deposit = 1`, or TIP-1094 `ZoneVirtual = 2`. Use their canonical ABI encoding. This commits the original sender, token, net amount, payload/destination, key index or mint provenance, refund action, and original memo without another context format. The receipt already binds the portal and token; its live balance authenticates custody. Receipt witnesses cannot create balances on another chain.

## Creating escrow

Add one guard entrypoint for funded ECIES overflow:

```solidity
/// @notice Escrow net principal already held by the calling canonical portal.
/// @param token Canonical TIP-20 whose portal balance is debited.
/// @param originator Original caller of the validated ECIES deposit.
/// @param amount Net amount after the ordinary upfront deposit fee.
/// @param depositHash Hash of the canonical type tag and queued-deposit struct.
/// @return receipt Existing ClaimReceiptV1 witness for this funded transfer receipt.
/// @dev Only a factory-registered canonical portal may call, after validating and
///      funding an overflow deposit. No allowance or transfer from originator occurs here.
///      Reverts UnauthorizedPortal for other callers, InvalidReceipt for zero amount,
///      or the ordinary token error if moving the caller's funds fails.
function escrowZoneDeposit(
    address token, address originator, uint128 amount, bytes32 depositHash
) external returns (bytes memory receipt);

error UnauthorizedPortal();
```

Native code moves `amount` from the calling portal's balance to the guard and allocates a `ZONE_CAPACITY`, `TRANSFER` receipt atomically. Treat this as custody for the portal after the original authorized inbound, not a new user transfer or another allowance spend. Maintain ordinary token balance/reward accounting and emit `Transfer(portal, guard, amount)` and the existing `TransferBlocked`. The guard need not parse deposit payloads or read queue capacity: the authenticated canonical runtime supplies validated fields and permits this call only from its funded overflow branch.

TIP-1094 native routing uses the same internal custody and receipt-allocation helpers after its ordinary validation, funding, and fee payment. It fixes originator and transfer/mint provenance from the originating TIP-20 operation, never from user-supplied portal arguments. The public ECIES entrypoint cannot create mint receipts. Preserve the original entrypoint's allowance, access-key, issuer, and supply-cap checks exactly once. Ordinary direct transfers to the guard remain forbidden.

## Admission and cancellation

Add two portal entrypoints:

```solidity
/// @notice Sequencer-only: claim a receipt and enqueue its immutable deposit atomically.
/// @param receipt Existing guard witness for this portal's pending overflow deposit.
/// @param encodedDeposit Canonical abi.encode(depositType, deposit) matching receipt.memo.
/// @return newCurrentDepositQueueHash Updated hash after appending the deposit.
function admitOverflow(bytes calldata receipt, bytes calldata encodedDeposit)
    external returns (bytes32 newCurrentDepositQueueHash);

/// @notice Originator-only: refund a pending transfer or cancel pending mint issuance.
/// @param receipt Existing guard witness; caller must equal receipt.originator.
/// @param encodedDeposit Same immutable encoded deposit used by admission.
function cancelOverflow(bytes calldata receipt, bytes calldata encodedDeposit) external;
```

Both methods require an open `ZONE_CAPACITY` receipt for this portal, the matching canonical deposit hash, and matching token, originator, amount, and transfer/mint kind. ECIES receipts must be transfer-originated; virtual `mintOrigin` must match `kind`. Invalid bindings use `InvalidReceipt()`; unauthorized callers use `UnauthorizedClaimer()`. Protect both methods against reentrancy and roll back the entire operation on failure.

`admitOverflow` requires the existing sequencer authority and current public capacity. Recheck current portal/token availability, depositor/refund permissions, and ECIES payload/key validity, using the committed original sender rather than the sequencer as depositor. Do not repeat funding, deposit-fee calculation, or the initial gross-amount minimum check. Call existing `claim(portal, receipt)` and append the committed deposit using the ordinary queue hash, counter, and deposit event, with the original sender and net amount. Claim and enqueue are atomic. The sequencer can select any pending receipt; no overflow FIFO is imposed. If a key expires or another validation fails, leave the receipt pending; its originator may cancel and submit a fresh deposit. This TIP adds no pending-key retention rule or grandfathered admission settings.

`cancelOverflow` requires `msg.sender == receipt.originator`, but no sequencer approval, active-deposit permission, portal unpause, membership, or capacity. For a transfer, call existing `claim(refundRecipient, receipt)`: use the committed ECIES refund recipient, or the original sender for a virtual transfer. Preserve the guard's current reroute checks, including the portal as policy subject. A failed claim leaves the receipt pending.

For a mint, call `claim(portal, receipt)` and then TIP-1094's proposed `cancelZoneDepositMint(amount)` in the same transaction. Extend that operation's canonical-runtime call-site restriction to accept an authenticated, just-consumed overflow mint receipt as well as a proof-authenticated queued mint failure. Burn exactly the claimed net amount from portal custody and Tempo supply. Never refund mint principal to the issuer or convert it into a transferable balance. A failed claim or burn restores the receipt and all balances. No new guard burn API or pause bypass is added: cancellation waits if the existing guard claim is blocked, even though TIP-1094's later queued cancellation has different pause rules.

Cancellation consumes the receipt without creating a queue entry. After admission, existing queued-deposit refund and mint-cancellation rules apply. Issuer `burnBlockedReceipt` remains governed by TIP-1028; a receipt it consumes is also unavailable for admission or cancellation.

## Results and events

A successful ECIES call returns the new queue hash if admitted immediately, or `bytes32(0)` if pending. Only actual enqueueing emits the ordinary queued-deposit event and assigns a deposit number. Withdrawal-callback paths must continue to append immediately and cannot return the pending result.

Keep ordinary initial funding, fee, and TIP-1094 logical transfer/mint events; overflow additionally emits the portal-to-guard custody transfer and guard `TransferBlocked`. Later admission emits the existing guard claim and normal deposit event, without replaying the original transfer/mint or fee. The virtual address never holds a literal balance.

# Tooling

Clients must distinguish pending capacity from queued and zone-credited states. Retain the receipt and encoded deposit for admission/cancellation, and preserve original virtual destinations and absent-versus-zero user memos. The receipt memo is a deposit commitment, not the user memo. An expired ECIES key requires cancellation and a fresh submission, paying its normal fee.

# Observability

Add one portal event to make the committed deposit data available:

```solidity
event ZoneDepositOverflowed(bytes32 indexed receiptKey, bytes encodedDeposit);
```

Emit it alongside `TransferBlocked`. Existing `ReceiptClaimed`, `ReceiptBurned`, token burns, and queued-deposit events identify subsequent outcomes. Correlate admission/cancellation transactions with their consumed receipt; no additional status ledger or lifecycle events are required. Track pending balances and age separately from active queue usage, with canonical-chain/reorg handling. Emit no decrypted recipient identifiers or keys.

# Threat Model

Canonical portal authentication and its restricted call paths prevent synthetic receipts, forged mint provenance, or use of unrelated portal backing. Native escrow code debits only its authenticated caller; it cannot spend an originator's funds or allowances. A mint-cancellation call must be backed by the same receipt consumed in that transaction.

Depositors can fill active capacity or create many receipts, paying normal transaction, storage, and deposit costs. Overflow-only removes capacity reverts but does not guarantee inclusion or prevent public deposits filling newly opened slots. Sequencers may select or delay admission; originators retain cancellation subject to ordinary claim restrictions. Issuer policy changes, token pauses, and issuer receipt burns keep their existing effects.

# Invariants

1. Initial success creates exactly one queue entry or one funded receipt; every non-capacity validation still applies.
2. Pending principal is backed by the guard, excluded from portal/zone liabilities, and creates no mandatory inbox work. Admission moves custody to the portal and creates exactly one queue entry atomically.
3. Admission, cancellation, and issuer burning consume the same single-use receipt. None can change its committed sender, recipient/payload, amount, memo, or mint provenance.
4. Fees are paid once upfront. Transfer cancellation refunds net principal; mint cancellation burns net principal and reduces Tempo supply by the same amount. Admission never mints again on Tempo.
5. Public queue bounds and withdrawal reserves remain unchanged. Any failed transition restores receipts, balances, supply, and queue state atomically.

Conformance tests must cover capacity boundaries and mixed deposit types; all virtual transfer/mint entrypoints; allowance and access-key metering; wrong portal, payload, token, amount, or mint provenance; non-capacity failures; fee collection exactly once; expired keys and changed permissions; both admission/cancellation race orders; issuer burns; paused/blocked claims; mint cancellation without general issuer roles; rollback and reentrancy; unchanged legacy receipts; callback reserves; event reconstruction and reorgs. Measure worst-case gas/storage costs before activation; this draft contains no runtime implementation.

# Alternatives considered

Escrowing every deposit changes the normal path unnecessarily. A separate escrow duplicates TIP-1028 accounting. Temporarily changing receive policy obscures the actual reason for escrow. Direct zone credit from an unconsumed receipt complicates cancellation races; claim-and-enqueue keeps the existing proof path.

# Success criteria

Otherwise-valid ECIES deposits and ordinary payments to TIP-1094 addresses succeed despite full public queue capacity. Pending principal can later be admitted once or cancelled through existing claim and mint-cancellation machinery, preserving queue bounds, refund authority, and mint provenance.
