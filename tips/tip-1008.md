# TIP-1008: Zone Deposit Overflow Escrow

## Abstract

An otherwise-valid zone deposit that exceeds public deposit-queue capacity succeeds into `ReceivePolicyGuard` instead of reverting. This adds a new source of receipts to the existing escrow, retaining its custody, receipt authentication, and single-use consumption. The zone later selects pending deposits for atomic claim-and-enqueue; the originator can instead cancel a pending deposit through the portal. Deposits with available capacity keep their existing path.

## Motivation

The zone deposit cap bounds mandatory zone execution and proof work. It currently also makes a temporary backlog fail a user's Tempo transaction, even when the funds, permissions, and deposit data are valid. Escrowing only overflow deposits preserves the cap while separating successful funding on Tempo from admission to the zone's mandatory queue.

[TIP-1094: Zone Virtual Deposit Addresses](https://github.com/tempoxyz/tempo/pull/7746) makes this especially useful: a wallet, exchange, or payment system sends an ordinary TIP-20 transfer to a reusable zone address, without constructing a portal call. That transfer should not fail solely because the zone's outstanding deposit queue is full. Its proposed mint entrypoints need the same capacity handling while preserving mint-origin cancellation. This TIP changes TIP-1094's capacity failure into a pending receipt; other validation failures still revert.

[TIP-1028](./tip-1028.md) already provides protocol custody and receipt-based recovery. Capacity exhaustion becomes another explicit reason for funds to enter that same escrow. No receive policy is temporarily changed, no policy rejection is fabricated, and no second escrow balance ledger is introduced.

## Assumptions

- Activation updates the Tempo guard and native token helpers, the canonical shared portal runtime, and clients together. Existing receipts and queued deposits retain their encoding and meaning.
- A caller claiming to be a portal is authenticated against the live native factory registry and the canonical shared runtime, not a supplied address or an address-prefix test. The runtime has no arbitrary call or delegatecall facility that could exercise its escrow privileges.
- Virtual deposits depend on TIP-1094 activation. ECIES overflow does not require virtual addresses. This TIP does not resolve the separate native-to-portal execution interface in that draft.
- Pending escrow depends on Tempo data availability and the immutable payload emitted at creation. Zone admission additionally requires an operating zone and accepted settlement that reopens capacity. Cancellation does not require zone execution, but ordinary transfer refunds remain subject to token pauses and current applicable policies.

# Specification

## Scope and Capacity

Apply overflow handling to public ECIES deposits and, when enabled, TIP-1094 virtual-address transfers and mints. Internal withdrawal bounce-backs, forced exits, and deposits returned through a withdrawal callback keep their existing reserved-capacity paths and callback success invariants.

Capacity remains the outstanding count `depositCount - lastProcessedDepositNumber`, using the existing public limit below `MAX_UNPROCESSED_DEPOSITS` and preserving the withdrawal-processing reserve. A new Tempo block does not reopen capacity; accepted batch settlement advances the processed cursor. Pending receipts do not change either counter or the queue hash and impose no mandatory work on `advanceTempo`.

Run every existing non-capacity admission check before accepting overflow: canonical token and enablement, portal/token pause, amount bounds and minimum, depositor and refund permissions, issuer authorization, and ECIES key/payload checks where applicable. Virtual routing also validates the address format, version, and registered zone. Preserve existing receive-policy behavior for these deposit paths; capacity fallback does not make an independently blocked deposit eligible. Insufficient funds, allowance, spending limits, issuer roles, and mint supply caps continue to revert.

If public capacity is available, enqueue normally and do not create a receipt. If it is unavailable and every other check passes, create exactly one overflow receipt and do not enqueue. A failed escrow operation rolls back the complete originating operation, including allowances, supply, balances, fees, and events.

## Existing Guard, New Receipt Reason

Append `ZONE_CAPACITY = 3` to TIP-1028's `BlockedReason`, retaining `NONE = 0`, `TOKEN_FILTER = 1`, and `RECEIVE_POLICY = 2`. `validateReceivePolicy` never returns `ZONE_CAPACITY`: only the authenticated deposit overflow path creates it.

Reuse `ClaimReceiptV1`, `balanceOf`, the global nonce, the receipt-key hash, and the existing receipt balance mapping without changing their layouts. An overflow receipt has:

| Field | Value |
|---|---|
| `version` | `1` |
| `token` | The actual deposited TIP-20 |
| `recoveryAuthority` | The registered portal |
| `originator` | Debited `from` for transfers; authorized mint caller for mints |
| `recipient` | The literal portal address, not a zone virtual address |
| `blockedAt`, `blockedNonce` | Existing guard timestamp and unique nonce |
| `blockedReason` | `ZONE_CAPACITY` |
| `kind` | `TRANSFER` or `MINT`, fixed by the authenticated funding path |
| `memo` | The deposit-context commitment below |

`balanceOf(receipt)` stores the gross principal. Funds occupy the token's existing aggregate guard balance. The literal virtual destination and original user memo are preserved inside the committed deposit context; neither is replaced with the portal address or context hash in application attribution. The guard never passes a zone virtual address through TIP-1022 resolution.

Define the canonical context as:

```solidity
struct ZoneDepositContextV1 {
    uint8 version;          // 1
    uint8 depositType;      // existing ECIES Deposit = 1; TIP-1094 ZoneVirtual = 2
    uint256 tempoChainId;   // Tempo chain ID at initial validation
    uint64 admissionBlock;  // Tempo block at initial validation
    uint128 depositFee;     // fixed fee validated at initial submission
    bytes deposit;         // abi.encode of the existing, net-amount queue deposit struct
}
```

For ECIES, `deposit` is the existing `Deposit` struct, including its original sender, token, net amount, refund recipient, key index, and entire encrypted payload. For virtual deposits it is TIP-1094's `VirtualDeposit`, including destination, originator, net amount, `mintOrigin`, `hasMemo`, and original memo. Only canonical ABI encodings are accepted. An ECIES context must have `kind = TRANSFER`; a virtual context's `mintOrigin` must match the receipt kind. Require the embedded token and originator to match the receipt and `netAmount + depositFee` to equal its guard balance without overflow.

The receipt memo is:

```text
keccak256(abi.encode(
    "TEMPO-ZONE-OVERFLOW-v1", context.tempoChainId, portal, context
))
```

Here `context` is the canonical `ZoneDepositContextV1` struct, not an independently supplied digest. The portal emits the full encoded context for later reconstruction. Creation requires `context.tempoChainId == block.chainid`; later validation uses the committed creation domain, preserving recovery if a future upgrade changes chain ID. The receipt binds that domain and the portal, rather than accepting a new domain at claim time.

## Creating Escrow

Extend the existing guard with one externally callable creation entrypoint for validated ECIES deposits:

```solidity
/// @notice Fund an overflow receipt for the calling registered portal.
/// @param token Canonical enabled TIP-20 being deposited.
/// @param from Original deposit caller whose tokens are debited.
/// @param grossAmount Principal before the fixed deposit fee.
/// @param context Canonical ABI-encoded ZoneDepositContextV1 validated by the portal.
/// @return receipt Existing ClaimReceiptV1 witness, usable with balanceOf and claim.
/// @dev Only the registered canonical portal may call. Uses its existing allowance
///      as spender; users do not approve the guard separately. Reverts on caller,
///      context, capacity, funding, or policy failure. Never calls Solidity back.
function escrowZoneDeposit(
    address token, address from, uint128 grossAmount, bytes calldata context
) external returns (bytes memory receipt);

error UnauthorizedPortal();
error InvalidZoneDepositContext();
error ZoneCapacityAvailable();
```

The canonical portal calls this only after validating an ECIES deposit and observing full public capacity, before collecting any funds or fees. It fixes `from` to that deposit's actual caller. The guard independently authenticates the portal and canonical token, confirms full public capacity from portal storage, validates the context's canonical encoding and field consistency, and requires its `admissionBlock` and `tempoChainId` to equal the executing Tempo block and chain ID.

Reject an unauthenticated portal with `UnauthorizedPortal()`, available public capacity with `ZoneCapacityAvailable()`, and a noncanonical encoding, unsupported context version/type, zero originator/amount, or inconsistent field with `InvalidZoneDepositContext()`. Only ECIES `depositType = 1` is accepted through this external creation entrypoint. Propagate ordinary token funding and policy errors. Unknown or consumed witnesses use the existing guard `InvalidReceipt()` error; claim/cancellation caller failures use `UnauthorizedClaimer()`.

Funding uses a restricted native TIP-20 helper with the same checks and effects as the portal's ordinary `transferFrom(from, portal, grossAmount)`: the spender for allowance purposes is the calling portal, and the logical issuer/receive-policy recipient is that portal. The helper credits the guard instead of the portal and creates the receipt atomically. This helper is internal to native execution; arbitrary callers cannot name a different spender or bypass receive policies. Do not first transfer funds to the portal and do not request a normal transfer to the reserved guard address.

For ECIES overflow, emit the token custody event `Transfer(from, guard, grossAmount)` and the receipt/overflow events below. There is no user memo on this funding leg; its encrypted memo remains inside the committed ECIES payload. TIP-1094 overflow uses the logical routing events defined below instead.

For TIP-1094, native transfer/mint routing uses the same internal receipt creation and custody helpers when its validated deposit encounters full capacity. The original entrypoint determines the spender, originator, issuer checks, and mint provenance. Transfers consume the original allowance exactly once; mints increase supply exactly once. Preserve normal access-key metering. A Solidity-callable API cannot select `MINT` or fabricate mint provenance.

All native paths use the same guard receipt allocator and balance mapping. The guard's ordinary public-transfer prohibition remains in force. This is an explicit capacity-escrow operation, not a receive-policy configuration change or a general permissionless escrow API.

## Pulling Deposits into the Queue

Add a sequencer-authorized portal entrypoint:

```solidity
/// @notice Atomically consume a pending receipt and append its committed deposit.
/// @dev Reverts without consuming the receipt if capacity, policy, or validation fails.
function admitOverflow(bytes calldata receipt, bytes calldata context)
    external returns (bytes32 newCurrentDepositQueueHash);
```

The portal requires the existing sequencer authority, checks the canonical context against the receipt commitment, validates all receipt fields above, and reads its nonzero gross balance. It rechecks public capacity, current portal/token availability and permissions, and current recipient-side policies needed for release. It then calls the existing guard `claim(portal, receipt)`, pays exactly the committed deposit fee to the current portal fee recipient, and appends exactly the committed net-amount deposit using the existing queue encoding, counters, and deposit event.

The fixed fee and initial ECIES key eligibility are preserved from creation; admission cannot silently increase the fee, change the recipient/payload/refund address, or treat a then-valid key as invalid merely because its admission window expired while waiting. Supporting nodes must retain pending deposits' ECIES keys and witnesses until resolution. If safe processing is no longer possible, leave the receipt pending for cancellation rather than enqueueing an unprocessable deposit. Current token, portal, or access restrictions may delay admission; cancellation remains a separate path.

Consumption, fee payment, and enqueueing are one atomic Tempo transaction under portal reentrancy protection. Any failure restores the receipt and all balances. There is no native-guard-to-EVM callback: the Solidity portal calls native guard operations and performs its own queue insertion. Never mint on the zone from a historical proof of an unconsumed receipt.

The sequencer may choose receipts in any order, with each admission using existing public capacity. There is no mandatory overflow FIFO or obligation to drain pending spam before admitting another receipt. Public deposits may still fill the active queue; overflow-only does not provide forced inclusion or eliminate that contention.

## Cancellation and Mint Provenance

Add an originator-authorized portal entrypoint:

```solidity
/// @notice Cancel a still-pending deposit without requiring sequencer cooperation.
/// @dev Requires msg.sender == receipt.originator and an authentic matching context.
///      Transfers refund to the committed address; mints cancel issuance by burning.
function cancelOverflow(bytes calldata receipt, bytes calldata context) external;
```

Cancellation verifies the same receipt/context binding, but does not require active deposits, portal unpause, membership, queue capacity, or sequencer approval. For a transfer receipt, the portal invokes existing `claim(refundRecipient, receipt)`: the ECIES refund address is committed in `Deposit`; a virtual transfer refunds its originator. The existing guard reroute checks, including the portal as policy subject and the destination's current receive policy, still apply. A policy or token-pause failure leaves the receipt pending for retry. Cancellation cannot redirect funds to an arbitrary caller-supplied address.

For a mint receipt, cancellation MUST NOT transfer funds to the mint caller or any beneficiary. Add:

```solidity
/// @notice Cancel issuance held by an authentic zone-capacity mint receipt.
/// @dev Only its registered canonical recovery portal may call; requires
///      blockedReason == ZONE_CAPACITY and kind == MINT. Consumes the entire
///      receipt and burns exactly its guard balance, reducing Tempo total supply.
///      Bypasses token pause, issuer roles, and policies only for this cancellation.
function cancelZoneOverflowMint(bytes calldata receipt) external;
```

The portal may invoke this only from `cancelOverflow` after originator authorization and context verification. Native validation authenticates the portal and mint receipt; a zero balance, forged provenance, wrong caller, wrong reason, or accounting mismatch reverts. Debit the guard aggregate balance and supply by the same full amount, clear the receipt, and emit the mint-cancellation event below plus token `Transfer(guard, address(0), amount)` and `Burn(guard, amount)`. No tokens are credited to zero. This does not grant general burn or mint authority and does not reuse the issuer's discretionary `burnBlockedReceipt` authorization.

No deposit fee is paid while waiting. Admission pays the fixed fee once; cancellation before admission returns or burns the full gross principal. Tempo transaction fees remain paid. Once admitted, cancellation fails because the receipt is consumed; later failures follow the existing queued-deposit refund or TIP-1094 mint-cancellation path, including their existing fees.

The existing `claim` and issuer receipt-burn operations remain available under their existing authority and policy rules. Issuer destruction of an eligible overflow receipt makes it unavailable for admission/cancellation and must be reflected in client status; there is no second claim against portal backing.

## Return Values and Virtual-Address Events

Existing ECIES `deposit` and `depositEncrypted` continue returning the new queue hash for immediate admission. They return `bytes32(0)` for overflow; this sentinel does not identify a queue entry. The receipt and explicit overflow event are authoritative for the pending result. Update callers that currently equate a successful call with immediate enqueueing. Reserved withdrawal callback paths must never return this pending result in place of their required deposit append.

An overflowed virtual operation emits its existing logical user-facing transfer/mint and optional user-memo events, but replaces TIP-1094's final virtual-address-to-portal custody leg with virtual-address-to-guard for the gross amount. Emit exactly one `TransferBlocked` and `ZoneDepositOverflowed`, and no queued-deposit event or fee payment. Immediate admission retains TIP-1094's existing events. Later guard release and the portal's normal deposit event identify admission without replaying the original logical transfer or mint.

# Tooling

Wallets, SDKs, explorers, and support tools must distinguish `PendingCapacity` from queued and zone-credited states even though the originating Tempo call succeeds. Expose the receipt, exact context, literal virtual destination where present, original memo, and current guard balance; provide sequencer admission and originator cancellation methods. Index the new reason without interpreting the context commitment as a user memo. Preserve absent-versus-zero virtual memos.

Rebuild state from guard and portal events, with canonical-chain/reorg handling. Admission assigns the ordinary deposit number only when queued. A pending receipt has no deposit number or recipient-private zone processing result. Pending keys must be retained until all associated receipts are admitted, refunded, burned, or otherwise consumed.

# Observability

Creation emits TIP-1028's existing `TransferBlocked` with `ZONE_CAPACITY`, plus:

```solidity
event ZoneDepositOverflowed(
    address indexed token, address indexed originator, bytes32 indexed receiptKey,
    bytes receipt, bytes context, uint128 grossAmount
);
event ZoneDepositOverflowAdmitted(bytes32 indexed receiptKey, uint64 depositNumber);
event ZoneDepositOverflowCancelled(bytes32 indexed receiptKey, bool mintOrigin);
event ZoneOverflowMintCancelled(
    address indexed token, bytes32 indexed receiptKey, uint256 burnedAmount
);
```

The portal emits the first three events after successful creation/admission/cancellation; the guard emits the final event only for its new mint cancellation. Ordinary releases also emit the existing `ReceiptClaimed`; issuer destruction retains `ReceiptBurned`. All events roll back on failure. `receiptKey` is the existing guard hash of the canonical receipt witness. A mint cancellation emits no `ReceiptClaimed` because nothing was transferred to a beneficiary.

Track pending count, principal, age, admissions, refunds, issuer burns, and mint cancellations by portal/token. Report active queue usage separately from pending escrow. Events expose only the deposit data already public on Tempo, never decrypted ECIES recipients, FF1 identifiers, or zone keys.

# Threat Model

Depositors may submit many valid deposits to fill active capacity or create many pending receipts. Tempo gas must cover per-receipt storage and emitted data; capacity escrow adds no free mandatory zone work. Sequencers can delay or selectively admit receipts; originators retain cancellation subject to transfer restrictions. Neither escrow nor admission grants forced inclusion.

The factory's portal authentication and canonical runtime are security boundaries: they prevent arbitrary callers from spending another portal's allowance, forging a validated context, fabricating mint provenance, or claiming unrelated receipts. Native helpers must not call untrusted tokens or Solidity while holding partially updated custody. Portal admission/cancellation are reentrancy protected and cannot be invoked through arbitrary-call facilities.

Issuer policy changes can delay transfer recovery, and an issuer may burn eligible receipts under TIP-1028. Pending mint cancellation reverses only authenticated issuance still held by that receipt; it cannot burn unrelated backing or turn a mint into a transferable refund. Zone operators must retain encryption keys for pending ECIES deposits; originators can cancel if admission becomes impossible.

# Invariants

1. Every successful user deposit initially creates exactly one queue entry or one funded overflow receipt. A full public queue alone never reverts an otherwise-valid scoped deposit.
2. An open receipt is backed only by its share of the guard aggregate balance. It is excluded from portal backing, active deposit commitments, and minted zone liabilities until atomic admission.
3. Admission consumes one receipt and moves gross custody to the portal, paying its committed fee and enqueueing the exact net deposit. Cancellation or issuer burning consumes that same receipt instead. No combination can create two claims on its principal.
4. The queue cap and withdrawal reserve are unchanged. Pending receipt count does not affect mandatory inbox/proof work, and receipt admission cannot bypass capacity.
5. Mint overflow increases Tempo supply once. Pre-admission cancellation reduces guard custody and supply by the full same amount; it never produces a refund balance. Admission does not mint again on Tempo.
6. Original sender, destination, payload, key, refund action, mint provenance, and memo semantics remain immutable. No receipt can be replayed across portals, tokens, or chain domains.
7. Failed creation, admission, refund, or cancellation leaves no partially consumed receipt, allowance, fee, supply change, or queue update.

Required conformance cases include exact capacity and capacity-minus-one; mixed ECIES/virtual deposits; all TIP-1094 transfer/mint entrypoints; transferFrom originator versus spender and unchanged portal allowances; ordinary and access-key metering; wrong portal/runtime/token and forged context/kind; non-capacity validation failures; byte-for-byte payload preservation and memo zero/absence; fixed fees and expired-but-retained ECIES keys; arbitrary receipt order; public-deposit contention and preserved callback/bounce-back reserves; current policy, pause, membership, and fee-recipient changes; cancellation while portal deposits are paused; cancellation/admission races in both orders; issuer receipt burns; mint cancellation under token pause and lost issuer roles; whole-transaction rollback and reentrancy; unchanged legacy receipts; virtual event routing and client pending/queued distinction; event reconstruction and reorgs; chain-domain retention; and worst-case escrow/admission gas and storage costs. These are implementation and activation requirements, not claims of implemented runtime tests.

# Alternatives Considered

- Temporarily reject the portal's receive policy: couples deposit admission to unrelated policy configuration and obscures why funds were blocked. An explicit capacity reason and authenticated funding path express the actual operation.
- Create a portal-specific escrow: duplicates custody and single-use receipt accounting already supplied by TIP-1028.
- Escrow all deposits: grants stronger screening and admission control, but changes the normal path unnecessarily. This TIP preserves immediate admission whenever public capacity exists.
- Grow or partially drain an unbounded mandatory queue: changes proof/work guarantees and leaves legitimate deposits behind mandatory backlog. Pending receipts remain outside that queue.
- Credit the zone directly from an unclaimed-receipt proof: complicates races with cancellation. Consume on Tempo before enqueueing instead.

# Success Criteria

An ordinary TIP-20 payment to a TIP-1094 address can succeed into the existing guard when only public queue capacity is exhausted. Both ECIES and virtual overflow deposits can subsequently be admitted exactly once or cancelled without sequencer cooperation, with authentic mint cancellation and preserved refund policies. Existing immediate deposits, queue bounds, withdrawal reserves, legacy receipts, and zone proof processing remain compatible. Activation requires implementation, adversarial conformance tests, and measured gas/storage costs.
